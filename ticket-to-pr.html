Q1 · What is it

An engineering org that fits in a folder

  • 18 agents — each one a .md file with a role, tools, a model and an output.
  • 1 orchestrator — the rto skill. It plans the run and dispatches agents.
  • A few bash scripts — selection, run-state, verify, Definition of Done.
  • 1 JSON config — risk weights, autonomy level, guardrails.

No framework. No vector DB. No custom runtime. It runs inside Claude Code.

Q2 · Why build it

Why not just “ask the AI”?

The pain

  • Every ticket: read, spec, design, plan, code, test, review, PR. Same steps, every time.
  • One long chat loses context and mixes jobs.
  • Agents say “Linter: PASS” when it didn't.
  • One big model for everything is slow and expensive.
  • Reviewing a transcript is harder than reviewing a diff.

Why plain markdown

  • Diffable — agent changes go through code review like any code.
  • Portable — copy a folder, not a platform.
  • Readable — a new hire can read the whole org in an afternoon.
  • Testable — bash scripts give exit codes, not opinions.

How · one agent

Anatomy of an agent file

---
name: qa-engineer
model: claude-haiku-4-5-20251001
description: >
  Writes and runs Pest 3 tests (Feature + Unit
  + arch()) for implemented changes. Every AC
  gets a test. Pattern-driven work — Haiku is
  optimal for speed.
tools: >
  mcp__sentrux__test_gaps, mcp__gitnexus__context,
  mcp__laravel-boost__DatabaseSchema, …
  Read, Grep, Glob, Bash, Edit, Write
maxTurns: 18
---
## Input     · artifacts it reads
## Tools     · a table: tool → when
## Workflow  · numbered steps
## Output    · 05-tests.md
## Rules     · Always / Never
## Harness Mechanism
  only your FINAL message reaches the
  orchestrator · turn budget · no user
  interaction · files are the only handoff
  • name — how the orchestrator calls it.
  • description — what it does and when. Write it for the dispatcher.
  • model — the cheapest one that does the job well.
  • tools — least privilege. QA can't push.
  • maxTurns — a hard stop, so it can't wander.
  • body — the same six sections in all 18 files.
  • Harness Mechanism — tells the agent how it's run: fresh context, one return message, no questions.
How · agent.md11
How · write your own

A template you can copy

---
name: <role-in-kebab-case>
model: <haiku | sonnet | opus>
description: >
  <One job.> <When to call it.> <Why this model.>
tools: <only what this job needs>
maxTurns: <8–35>
---
# <Role>
You are the <role> in an automated pipeline.
## Input
Read: artifacts/<KEY>/<NN-previous>.md
## Tools
| tool | when to use it |
## Workflow
1. …  2. …  3. …
## Output
Write: artifacts/<KEY>/<NN-mine>.md
### Verdict: PASS / FAIL / WARN
## Files Changed       # if you can Edit
FILE: app/Services/Foo.php
## Rules
NEVER commit, push, or create branches
NEVER edit files outside your scope
## Harness Mechanism
Only your final message returns. No questions.

Six sections, always the same order.

  • Inputs and outputs are file paths, not vibes.
  • One parseable verdict a script can grep: ### Verdict:
  • Anyone with Edit ends with FILE: lines — that's the commit list.
  • The Never list is shorter and stronger than the rules list.
  • Put examples of good output in the file — the model copies them.

How · lessons from real runs

Best practices for agent files

  • One job per agent. A reviewer that also fixes, reviews its own fixes.
  • Least tools. Reviewers get Write for their report, never Edit. Anyone with Edit must list what they touched.
  • Name the artifact it reads and the one it writes.
  • Cap the turns. Turn limits are a cheap budget.
  • Rules go in bash, judgement in markdown. If it can be an if, it's not a prompt.
  • Never trust a self-report. Re-run the linter yourself.
  • Say what not to do. “Do NOT rewrite the spec yourself.”
  • Version it. Agent edits get code review, like any change.
How · best practices13
How · the conductor

The orchestrator never commits

  • One skill file: skills/rto/SKILL.md. It's a runbook, step by step.
  • It calls agents, runs scripts, reads artifacts and opens gates.
  • Agents leave changes in the working tree only.
  • Commit, push and PR happen once, after Gate 3.
  • It stages only files agents declared in ## Files Changed — never git add .
## Commit & Branch Policy (enforced)
- Agents NEVER commit or push during
  the pipeline. All changes land in
  the working tree only.
- Commits/push/PR happen exactly once
  — at Step 12, AFTER explicit Gate 3
  approval.
- The pre-push hook blocks --no-verify
  — never bypass it; if it fails, fix
  the cause.
- Stage only files declared in the
  agents' Files Changed manifests.

pipeline-state.sh — resumable, with ceilings

pipeline-state.sh init       gh-123
pipeline-state.sh set-phase  gh-123 plan done
pipeline-state.sh record-dispatch \
        gh-123 qa-engineer 212 true
pipeline-state.sh guardrail  gh-123
  # exit 1 when a ceiling is hit:
  #   maxTicketTokens  400000
  #   maxAgentRuns         14
  #   maxFixRetries         2
pipeline-state.sh resume     gh-123
  # → next phase + what to do
  • The run state lives on disk, not in the model's memory.
  • Check the guardrail before every dispatch. Tripped → stop and show a human.
  • Tokens are recorded only when measured. No estimates.
  • Resume never redoes a finished phase.

How · bash, not hype · 3 of 3

Don't trust “PASS”. Check the exit code.

# Step 8.2 — anti-hallucination gate
CLAIMED=$(grep -i 'Linter|Syntax' \
   04-implementation.md)       # what it says
bash ci-toolkit/scripts/ci/verify.sh gh-123
VERIFY_RC=$?                    # what it is

# rc 1 → re-dispatch with the real errors
#        (max 2), then stop and ask

# Gate 3 — Definition of Done as a script
PEST_FULL=1 bash dod-check.sh gh-123
# 0 = artifacts exist, tests reference
#     tests/, review says PASS,
#     lint + types + full suite pass
  • verify.sh re-runs pint, phpstan, syntax and Pest on the changed files.
  • An agent that claims success and fails here either erred or lied. Both get the real errors back.
  • dod-check.sh makes “done” a number: 0 or 1.
  • Missing tool = skip with a warning. Only real violations fail.
How · verify & DoD17
How much to trust it

The autonomy dial

0Every gate human.
The default. Start here.
1Gates 1–2 auto for low-risk tickets. Gate 3 stays human.
2Gate 3 auto too: commit, push and PR without asking — if eligible.
3Factory mode: a driver claims queued tickets.

“Eligible” means all of:

  • risk LOW or MEDIUM
  • bugfix, refactor or docs
  • confidence ≥ 0.55
  • no exclusion signal
"autonomy": {
  "level": 0,
  "autoGateMaxRisk": "MEDIUM",
  "autoGateTypes": ["bugfix","refactor",
                    "documentation"],
  "minConfidence": 0.55

The parts that never go automatic

Guardrails: some doors stay locked

Always human

  • Payments — Stripe, QuickBooks, anything with money
  • Migrations — schema changes are hard to undo
  • Auth & security — roles, tokens, passwords
  • Tenancy — one customer's data, another's screen

At any autonomy level, these four force a human Gate 3. So does an issue with instruction-like text in it (## Suspicious Content) — then every gate is human.

Guardrails19
Why the human stays

Why a human stays in the loop

Accountability

Someone signs the PR. An agent can't be on call at 3 a.m.

Irreversibility

A bad migration or a wrong charge can't be reverted with git revert.

Confident errors

Models are most sure when they're wrong. A human spots “that's not what we meant”.

Intent

The ticket says what. Only people know why — and when to say no.

Trust is earned

Start at level 0. Raise the dial only on ticket types with a clean record.

Cheap review

The human reads a diff + verdicts + DoD box — 2 minutes, not a transcript.

Where the human looks

Three gates, and what replaces you at each

Gate 1 · Spec

Do the acceptance criteria match the issue?

Auto path: the CTO agent red-teams the spec — untraced criteria, missing ones, untestable ones.

Gate 2 · Plan

Is the plan safe for the blast radius?

Auto path: pr-reviewer red-teams the plan — the CTO wrote the ADR, so it doesn't grade it.

Gate 3 · Ship

Commit, push, PR?

Auto only at level 2 and DoD = 0 and review is fresh and no undeclared files and no exclusion.

Rating · what could actually go wrong

Four run-order bugs — fixed in SKILL.md

What was wrongThe fix
Reviewed diff ≠ shipped diff. pr-reviewer ran, then the full-suite verify could trigger more fixes that nobody reviewed.pr-reviewer now runs after the full-suite verify. A fingerprint records the code it saw; if the code changes later, verify + review run again (Steps 9 and 11).
The commit could miss files. Only 04-implementation.md + tests/ were staged, so performance and docs edits were left behind.Every agent with Edit ends its artifact with FILE: lines. Gate 3 compares them with git status: any undeclared file stops the run. Step 12 stages only declared files.
pr-reviewer ran twice — in the sequential phase and again at Step 9.Sequential phase is qa-engineer only. pr-reviewer runs once at Step 9; post-review agents moved to Step 9.5.
Gate 2 graded its own work. The CTO checked a plan built on its own ADR.pr-reviewer red-teams the plan. The CTO still checks the spec, which it didn't write.

Two new checks before Gate 3

# 1. was the shipped code reviewed?
review_fp() {   # artifacts excluded, new files included
  { git diff "$BASE_BRANCH" -- . ':(exclude).claude/artifacts'
    git ls-files --others --exclude-standard -z \
      -- . ':(exclude).claude/artifacts' | xargs -0 shasum
  } | shasum | cut -c1-12
}
review_fp > $ART/.review-fp       # Step 9

# Step 11
[ "$(review_fp)" != "$(cat $ART/.review-fp)" ] &&
  echo "code changed after review → verify + review"
# 2. is every changed file accounted for?
DECLARED=$(grep -hE '^FILE: ' $ART/*.md \
           | cut -c7- | sort -u)
ACTUAL=$(git status --porcelain --untracked-files=all \
         -- . ':(exclude).claude/artifacts' \
         | cut -c4- | sed 's/.* -> //' | sort -u)
UNDECLARED=$(comm -13 <(echo "$DECLARED") <(echo "$ACTUAL"))
STAGE_LIST=$(comm -12 <(echo "$DECLARED") <(echo "$ACTUAL"))

# undeclared → no auto path, shown above Gate 3
# Step 12 stages STAGE_LIST only, one path at a time

Agents are code. Code gets a linter.

# .claude/skills/rto/agent-lint.sh — rto pre-flight step 10
for f in "$AGENTS"/*.md; do
  n=$(basename "$f" .md); fm=$(awk '/^---$/{c++;next} c==1' "$f")
  for k in name model description tools maxTurns; do
    grep -q "^$k:" <<<"$fm" || err "$n: frontmatter missing '$k'"; done
  case $n in *-reviewer|security-engineer|qa-engineer|…)
    grep -q '^### Verdict: ' "$f" || err "$n: no '### Verdict:' line";; esac
  case $n in *-reviewer|security-engineer|sentrux-quality-gate)
    grep -qw Edit <<<"$tools" && err "$n: reviewer has the Edit tool";; esac
  grep -qw Edit <<<"$tools" && ! grep -q 'Files Changed' "$f" &&
    err "$n: has Edit but no Files Changed manifest"
done
for a in $(grep -oE 'Agent\([a-z-]+\)' "$SKILL" | …); do
  [ -f "$AGENTS/$a.md" ] || err "SKILL dispatches '$a' — no such file"
done
grep -qE '^\| *[a-z-]+ *\| *`claude-' "$SKILL" &&
  err "SKILL repeats a model table — frontmatter is the source of truth"
