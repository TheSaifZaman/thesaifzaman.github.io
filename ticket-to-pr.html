What
WhatFoundations

What is “agentic” development, actually?

A model in a loop: it picks the next step from what the last step returned.

Read a file → run the tests → see the failure → edit → run again. The model doesn't just answer; it acts and checks.

Autocomplete

Suggests the next line. You drive.

Chat

Answers questions. You copy, paste, run.

Agent

Acts, observes, repeats — inside one context.

Agent team

Many agents, one job each, scripts and gates around them. This talk.

What
WhatFoundations

What does a real setup contain? Four building blocks.

Hooks

Always run. No model decides.

  • scan every prompt for secrets
  • format the file just edited
  • architecture check after an edit

Skills

Runbooks loaded into the main session.

  • /rto — ticket to PR
  • plan → apply → unify workflow
  • migration, release notes, API docs

Agents

Workers with a fresh context and one job.

  • 18 roles: analyst → reviewer
  • one file each
  • return one message

MCP tools

Senses — what agents can see.

  • code graph: callers, blast radius
  • DB schema and framework docs
  • memory across sessions
# a hook, three stacks — runs after every file edit, no model involved
case "$FILE" in
  *.php)            vendor/bin/pint "$FILE" ;;        # PHP / Laravel
  *.ts|*.tsx|*.js)  npx prettier --write "$FILE" ;;   # TypeScript / JS
  *.go)             gofmt -w "$FILE" ;;               # Go
esac
Why
WhyMotivation

Why not one big agent in one long chat?

Context rot

Hour two of a chat: early decisions fall out of view, and the model contradicts them.

Mixed jobs

The same head writes the spec, the code and the review. It agrees with itself.

Self-reports

“Linter: PASS.” It didn't run the linter. Nothing checked.

Cost

The biggest model reads everything, including the parts a small model handles fine.

Every one of these bit me on real tickets. → Split the jobs, check the claims, size the model to the job.

spec, code AND review?!
Why
WhyMotivation

Why plain markdown and bash, not a framework?

  • Diffable — a prompt change is a merge request, reviewed like code.
  • Portable — copy a folder, not a platform. Works in any repo, any language.
  • Readable — a new hire reads the whole team in an afternoon.
  • Testable — scripts return exit codes, not opinions.

What it isn't

No server. No vector database. No custom runtime. No SDK to learn.

It runs inside the agent tool you already have.

If it can't be reviewed in a merge request, it will drift.

  • Config holds the numbers you'll tune.
  • Artifacts are the audit trail — kept forever.

Porting to TypeScript or Go = rewrite verify.sh and each agent's “stack” section. The rest stays.

HookSkillAgent
RunsOn every matching eventWhen invoked, in the main sessionWhen dispatched, in a fresh context

Use forMust always happenA procedure, a workflow, orchestrationA focused job that needs a clean head
ExampleFormat on save · secret scanWrite release notes · the ticket pipelineSecurity review · red-team a plan

The orchestrator is a skill. Everything it dispatches is an agent.

WhenThe pipeline

When does each agent run? /rto gh-123, end to end.

How
HowBuilding

How do I write an agent that behaves?

---
name: qa-engineer
model: haiku             # cheapest that does it well
description: >
  Writes and runs tests for the changed code.
  Every acceptance criterion gets a test.
tools: Read, Grep, Glob, Bash, Edit, Write
maxTurns: 18               # a hard stop
---
## Input     01-spec.md, 04-implementation.md
## Stack     Pest | Vitest | go test — swap per repo
## Workflow  1. … 2. … 3. …
## Output    05-tests.md, ends with:
### Verdict: PASS | FAIL | WARN
## Files Changed
FILE: tests/Feature/InvoiceTest.php
## Rules
NEVER commit, push or create branches
## Harness
Only your final message returns. No questions.
  • One job. A reviewer that also fixes, reviews its own fix.
  • Fewest tools. Reviewers write a report, never edit code.
  • Files in, file out. Paths, not vibes.
  • A verdict a script can grep.
  • Declare what you touched with FILE: lines.
How
HowVerification

How do I know it isn't lying? Re-run everything.

# verify.sh — the agent's claim vs the exit code
case "$STACK" in
  php) vendor/bin/pint --test $FILES
       vendor/bin/phpstan analyse $FILES
       vendor/bin/pest --dirty ;;
  ts)  npx prettier --check $FILES
       npx eslint $FILES && npx tsc --noEmit
       npx vitest run --changed ;;
  go)  test -z "$(gofmt -l $FILES)"
       go vet ./... && go test -race ./... ;;
esac
VERIFY_RC=$?
  • The orchestrator never reads the claim. It reads the exit code.
  • Exit 1 → the real errors go back to the agent.
  • Two tries at most, then a human.

How
HowResilience

How does it survive a crash halfway through?

pipeline-state.sh init       gh-123
pipeline-state.sh set-phase  gh-123 plan done
pipeline-state.sh record-dispatch \
        gh-123 qa-engineer 212 true
pipeline-state.sh guardrail  gh-123
  # exit 1 when a ceiling is hit:
  #   maxTicketTokens  400000
  #   maxAgentRuns         14
  #   maxFixRetries         2

/rto gh-123 --resume
→ {"nextPhase":"plan","action":"read 02-adr.md"}
  • State lives on disk, not in the model's memory.
  • 14 named phases; resume never redoes a finished one.
  • Check the ceiling before every dispatch. Tripped → stop and show a human.
  • Tokens are recorded only when measured. No estimates.

Budgets are guardrails too — a runaway loop is a cost incident.

How
HowDelivery

How does code get committed? Once.

  • Agents change the working tree only. No branches, no commits.
  • The pr-reviewer runs last and fingerprints the code it saw. Code changed since? Test and review again.
  • One commit, one push, one PR — after Gate 3.
  • Hooks are never bypassed. If a hook fails, fix the cause.
How
HowDelivery

Is every changed file accounted for?

# what agents say they changed
DECLARED=$(grep -hE '^FILE: ' "$ART"/*.md | cut -c7- | sort -u)
# what actually changed
ACTUAL=$(git status --porcelain --untracked-files=all | cut -c4- | sort -u)

UNDECLARED=$(comm -13 <(echo "$DECLARED") <(echo "$ACTUAL"))
STAGE_LIST=$(comm -12 <(echo "$DECLARED") <(echo "$ACTUAL"))
  • Undeclared file? The automatic path stops, and a human sees it.
  • Stage the declared files one by one — never git add .
How much
How muchTrust

How much should I let it decide? Turn a dial.

0Every gate human. The default. Start here.
1Gates 1–2 automatic for low-risk tickets, checked by a critic agent. Gate 3 human.
2Gate 3 automatic too — commit, push, PR — when every check passes.
3Factory: a separate driver picks up queued tickets.

Eligible for automatic gates — all of:

  • risk LOW or MEDIUM
  • bugfix, refactor or docs
  • confidence ≥ 0.55
  • no locked door

Config: autonomy.level in agent-selection-config.json — default 0. The env var AUTONOMY_LEVEL overrides it.

much
How muchTrust

What must never go automatic? Four locked doors.

Payments

Stripe, any money movement.

Migrations

Laravel, Prisma, goose — schema is hard to undo.

Auth & security

Roles, tokens, passwords.

Tenancy

One customer's data on another's screen.

Any of these forces a human Gate 3 at every level. Suspicious text in the issue makes every gate human.

How much does the human read? Three boxes, two minutes.

Gate 1 · Spec

Do the acceptance criteria match the issue?

Automatic: the CTO agent red-teams the spec.

Gate 2 · Plan

Is the plan safe for the blast radius?

Automatic: pr-reviewer red-teams it — the CTO wrote the ADR.

Gate 3 · Ship

Commit, push, open the PR?

Automatic only at level 2 with every check green.

──── GATE 3: Ready to Commit + PR ────
Type / Target:  bugfix → PR base `main`       Autonomy: level 0 → gate3=human
Diff:           6 files changed, 212 insertions(+), 14 deletions(-)
Review:  PASS (fingerprint 3fa9c1e2b7d0 = current tree)   Tests: PASS (changed + full suite)
Manifest: 7 files declared, 0 undeclared                 Structure: 7420 → 7455 ✓
Approve commit + push + PR? [yes | no + feedback]

You review a diff and verdicts — never a transcript.

The threat

Anyone can write an issue. Agents with a shell read it.

The defence, in layers

  • Issue text is data, never instructions.

Quiz
CheckCan you run it in your head?

Four scenarios. Answer, then check.

1. Autonomy is 2. The ticket changes the Stripe webhook. Does Gate 3 go automatic?

No. Payments is a locked door at every level.

2. The builder reports “all tests pass”. verify.sh exits 1. What happens?

The real errors go back to the builder — twice at most, then a human.

3. Every Go file must be gofmt-ed after each edit. Hook, skill or agent?

Hook. It must always happen and needs no judgement.

4. The security reviewer finds a bug. Should it fix it?

No. It reports. One job per agent; reviewers have no Edit tool.

Where is agentic development heading? My bets.

01Specs become the source. Clear acceptance criteria matter more than clever prompts.
02Evals become the test suite for agent behaviour — run on every prompt change.
03Agents run in the background; humans review in batches at gates.
04Engineers become editors and system designers — fewer keystrokes, more judgement.
05Guardrails move into the platform: permissions, budgets and audit trails built in.

Opinions, not forecasts. The patterns in this talk hold either way: small jobs, files, scripts, gates.
